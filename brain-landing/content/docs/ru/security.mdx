# Модель безопасности

Гарантии слой за слоем — в том порядке, в котором их проходит запрос.

## 1. Аутентификация

Brain принимает два auth-примитива, оба в форме JWT:

- **Пользовательские / сервисные токены с проверкой по JWKS** — выпускает `auth.inite.ai`, audience `brain`. Brain подтягивает JWKS на старте и при ротации.
- **Статические `BRAIN_API_KEYS`** — JSON-массив `{keyHash, companyId, scopes}` в env. `keyHash` — это `sha256:<hex>` от открытого ключа. Открытый текст не хранится никогда.

В проде работает только JWT. Статические ключи — dev-фолбэк; `validateEnv()` предупреждает, если они заданы при `NODE_ENV=production`.

## 2. Авторизация (scopes)

Каждый эндпоинт объявляет требуемый scope. Несовпадение = 403 ещё до бизнес-логики.

| Scope | Кому нужен |
| --- | --- |
| `brain:read` | Все `/v1/search*`, `/v1/entities/:id` (поля без PII), чтение доверия `/v1/sources`, поиск по реестру паков (`/v1/registry/*`), MCP-инструменты чтения |
| `brain:write` | `/v1/ingest/*`, `/v1/facts/:id/retract`, MCP-инструменты записи (`record_fact`, `retract_fact`, …) |
| `brain:read_pii` | Открывает значения чувствительных предикатов (`email`, `phone`, `dob`, `address`) |
| `brain:admin` | Операции тенанта: `/v1/entities/:id/forget`, `/v1/dreams/run`, установка / удаление Domain Packs (`/v1/admin/packs*`, включая установку из реестра), переиндексация документов (`/v1/admin/documents/reindex`), админ-конфиг |
| `registry:publish` | Публикация / yank в **глобальном** реестре паков, профили издателей, цены на паки — отдельный от `brain:admin` scope, потому что меняет общий для всех тенантов каталог |
| `registry:curate` | Кураторство глобального реестра оператором хостинга (feature / unfeature) |
| `indexer:write` | Внешние индексеры: poll / claim рабочих слотов, чтение контента доставшихся документов, стейджинг кандидатов (`POST /v1/documents/:id/candidates`) — намеренно у́же, чем `brain:write`: может предлагать гипотезы, но никогда не коммитит факты |

Проверка PII-scope продублирована в общем фильтре чтения на каждой поверхности (см. «Гейтинг PII» ниже). Баг в одном контроллере не приведёт к утечке — общий фильтр не отдаст значение.

## 3. ABAC-политики

Scope отвечает на вопрос «можно ли этому ключу вообще искать» — но не на вопрос «можно ли этому ключу видеть факты из HR-документов». ABAC добавляет именованные **policy-наборы**, которые тенант прикрепляет к отдельным API-ключам:

- **Правила действий** разрешают / запрещают REST-эндпоинты и MCP-инструменты по имени (`search_knowledge`, `rest.documents.get`, …) или через макросы `@readonly` / `@write` / `@all`. Инструменты из паков гейтятся по их конкретным именам `<packId>__<tool>`.
- **Правила источников** фильтруют, какие *строки* ключ может читать, по атрибутам провенанса факта: предикат, PII-класс, вертикаль / рекордер источника, происхождение документа, метаданные оператора, **числовые пороги доверия** (`trust.authority`, `trust.learnedTrust`), количество подтверждений, per-user scope.

Вычисление — deny-overrides (`явный deny > явный allow > дефолтная поза`); несколько наборов складываются по принципу «самый строгий побеждает». Всё инертно, пока не выставлен `ABAC_ENABLED=1` **и** ключ не ссылается на набор — тенант без политик работает байт-в-байт как до ABAC.

Раскатка спроектирована безопасной: создаёшь набор в режиме `report_only`, смотришь на решения `would_deny`, потом переводишь в `enforce`. Симуляция **Key Lens** (`POST /v1/admin/policy/simulate/search`) прогоняет настоящий поиск так, будто его выполняет заданный ключ, и помечает каждую строку вердиктом и причинами — ты видишь, что именно спрячет политика, ещё до её включения.

Полная модель, таблица атрибутов и ранбук раскатки: [`docs/abac.md`](https://github.com/inite-ai/inite-brain-service/blob/main/docs/abac.md).

## 4. Изоляция на тенанта

У каждой компании своя база SurrealDB `co_<companyId>` внутри общего namespace `inite`. **Общей таблицы с row-level security нет** — кросс-тенантные запросы физически невозможны на уровне хранилища.

Scoped-подключение к БД заходит как `brain_caller` — editor-пользователь без root-прав. Root-креденшалы зарезервированы под `DEFINE` / `REMOVE`. Миграции схемы применяются на тенанта при первом запросе через идемпотентные `DEFINE … IF NOT EXISTS`.

## 5. Привязка companyId в MCP

Каждый MCP-запрос несёт companyId в пути URL. Контроллер brain проверяет `pathCompanyId === auth.companyId` и на несовпадение отвечает `400`. Ключ, выданный для `co_demo`, нельзя использовать против `/mcp/co_other`.

## 6. Гейтинг PII

Каждая поверхность чтения проходит через общий scope-aware фильтр, который скрывает поле `object` чувствительных предикатов для вызывающих без `brain:read_pii`. Параллельный DB-фенс через `PERMISSIONS` на `knowledge_fact` определён как defence-in-depth (канареечный e2e ждёт релиза SurrealDB, где field permissions начнут действовать на системных пользователей; активный барьер сегодня — фильтр на уровне приложения, и его покрытие каждой поверхности закреплено e2e-тестами).

Вызывающий без scope всё равно видит, что строка существует — `predicate`, `validFrom`, `factId` на месте. `object` приходит как `null`. Это сигнал «данные у нас есть, прав у тебя нет».

CI гоняет eval гейтинга PII с порогом 1.0 — любая утечка блокирует релиз.

## 7. GDPR-forget

`POST /v1/entities/:id/forget` каскадом проходит по фактам, рёбрам, эмбеддингам, производным артефактам. Синхронно. Оставляет tombstone `HMAC(forgetHmacKey, entityId)` в `forgotten_entity`. HMAC доказывает, что запрос выполнен, не храня id сущности открытым текстом.

`FORGET_HMAC_KEY` обязателен в проде — `validateEnv()` жёстко роняет сервис, если он отсутствует или дефолтный. С дефолтным ключом злоумышленник может подделывать tombstone'ы.

## 8. Audit trail

Каждый retract / forget / запуск dreams попадает в audit-таблицу с идентичностью вызывающего, таймстампом и причиной. Audit-строки неизменяемы (на уровне БД — нет прав на UPDATE / DELETE). Retract-каскад перечисляет каждый производный факт.

## 9. Rate limiting

На тенанта и на эндпоинт через `@nestjs/throttler`. Дефолты:
- `/v1/ingest/*` — 100 req/min
- `/v1/search` — 600 req/min
- `/v1/synthesize` — 60 req/min (стоимость LLM)
- `/v1/dreams/run` — 1 req/hour

Переопределяется на тенанта через админ-API. В заголовках — `X-RateLimit-Remaining`.

## 10. Валидация на старте

`validateEnv()` выполняется до запуска NestJS. Отсутствующие или битые значения дают одну многострочную ошибку и exit code 1. Лучше отказаться стартовать, чем сыпать 500-ми под нагрузкой.

## 11. Graceful shutdown

`SIGTERM` / `SIGINT` закрывают соединение с SurrealDB и дожидаются запросов в полёте. Дедлайн 15 секунд — чтобы docker / fly / k8s не прислали `SIGKILL` посреди запроса.

## API доверия к источникам

Входные данные доверия читаемы, а не секретны: `GET /v1/sources` (список, фильтры `domain` / `type` / `minSamples`) и `GET /v1/sources/:sourceKey` (детально) доступны любому ключу с `brain:read`. Они отдают то, что нужно потребителю, чтобы взвесить trust-снапшот факта: заявленный тип источника и уровень authority, выученные agreement rate (глобальный и по доменам, со счётчиками sample / win / loss) и ограниченную историю репутации (не больше 50 строк). Аннотации оператора (`owner`, `note`) остаются на поверхности `brain:admin` — публичная проекция их не отдаёт никогда.
