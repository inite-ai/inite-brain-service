# Conflict resolution

When a new fact meets an existing value of the same slot (entity, predicate, overlapping valid window), brain settles it in two steps. At write time it applies only rules that need no judgement, and valid time decides. A pair valid time cannot order goes to fact resolution, where a judge names the relation. Nothing is scored: there are no weights, no margin and no reject floor.

## At write time: valid time decides

| The new fact… | Outcome | What happens |
| --- | --- | --- |
| states the same object (or restates it) | **CORROBORATED** | Stored as `corroborating`, pointing at the value it confirms. The original stays the active row. |
| starts strictly later than a value of the slot | **SUPERSEDED** | The earlier value closes at the new fact's `validFrom` (status `superseded`). The new fact is active. |
| starts strictly earlier than a value of the slot | **INSERTED_HISTORICAL** | The new fact goes straight to history, closed where the later value starts. |
| holds from the same moment with a different object | **INSERTED** (`reason: for_resolution`) | Both stay active; fact resolution judges the pair. |

By predicate semantics:

- `single_active` (`name`, `email`, …) — one value at a time: every value that overlaps the new one in valid time closes where it starts.
- `bitemporal` — the rules above, among values that are about the same object (cosine above the similarity threshold) and overlap in valid time.
- `bitemporal_event` — the same rules by calendar day; two different values on the same day are both marked `competing`.
- `append_only` — never closes anything; an exact restatement from another origin corroborates.

Confidence, source trust and authority are recorded on every fact (`trustSnapshot`) as provenance. They do not decide a conflict. The fact's `conflictTrace` says what did: `decidedBy: 'valid_time'` or `'event_day'`, and which facts it closed.

## Fact resolution: the judge names the relation

For each new fact, a judge compares it with the most similar facts on the same entity and answers one of:

- **same** — a paraphrase or confirmation: the new fact corroborates.
- **replaces** — successive values of one attribute: valid time decides which one closes.
- **contradicts** — the same attribute at the same time, two values that cannot both be true: both are marked `competing`.
- **unrelated** — nothing changes.

`COMPETING` therefore marks a real disagreement, never a close score. Search shows both values, marked `[competing]`, so a dispute is never hidden behind one side.

A fact from a system of record (`source.kind = 'source_record'`, a CRM or database door) keeps its slot: the judge never changes its status. A claim that disputes it is marked `competing` beside it. To change the record's value, change it in the source system; the next sync supersedes it.

## A worked example

Tenant: `co_demo`. Predicate: `tier` (bitemporal).

Existing fact:
```
predicate: tier, object: gold, validFrom: 2026-02-01, source: rent
```

New ingest:
```
predicate: tier, object: platinum, validFrom: 2026-04-01, source: inbox
```

The platinum fact starts strictly later, so `gold` closes at 2026-04-01 and `platinum` is the active value. The timeline keeps both: gold for February and March, platinum from April. Which source said it is on each fact; it did not change the outcome.

If the inbox had said `platinum` from 2026-02-01, the same moment as `gold`, both would stay active and fact resolution would judge them. Two different tiers for the same customer from the same day contradict, so both become `competing` until a later value, the dreams resolver or a person settles it.

## Dreams resolver

Off-hours, `dreams_resolve` takes `COMPETING` pairs aged > 7 days. An LLM judge picks a winner using surrounding entity context; the loser is marked `superseded` with `retractionReason='dreams_resolution'`. Conservative — an `unsure` verdict leaves both for human review. Groups of three or more always wait for a person.

Enable via `DREAMS_RESOLVE_ENABLED=1`. Bounded by `DREAMS_RESOLVE_MAX_PAIRS` (default 20).

## Dead-letter

A fact is rejected only when the store could not create the row (`REJECTED`, `reason: create_returned_none`). It lands in `ingest_dead_letter` with the reason, so an operator can see a write that never arrived. A low-confidence or low-trust fact is never dropped: it is stored, and its provenance says how much to trust it.
