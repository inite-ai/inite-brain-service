A general-purpose agent memory has to speak a generic language: `name`,
`status`, `preference`, `located_in`. That's the right default — it works
everywhere. It's also not enough the moment your agent works somewhere
*specific*.

A real-estate agent needs to remember that a property is `zoned_as R-2` and
`valued_at $540k`. A clinical assistant needs `diagnosis` and `medication`, each
carrying the right PII class. You can bolt these on by forking the core and
hard-coding a vocabulary — and then you own a fork forever. Domain Packs are the
alternative.

## Ontology as a module, not a fork

A Domain Pack is a manifest: a versioned bundle of **predicates** the memory
should understand, each with its datatype, conflict semantics, and PII class —
plus optional **extraction guidance** that tunes how the model pulls those facts
out of text. Install it into a tenant and, with no redeploy, the memory starts
storing those facts as first-class, typed, queryable citizens of the graph.

The core stays generic. The vertical vocabulary rides on top, per tenant, as
data.

## Namespacing keeps it safe

Two packs will eventually both want a predicate called `status`. So every pack
predicate is stored namespaced — `<packId>__<localId>` — which means
`real_estate__status` and `hr__status` coexist, and neither can shadow a core
predicate. The loader checks this at install and **refuses any collision** rather
than silently overriding. A bad pack fails loudly; it never quietly corrupts the
vocabulary another pack or the core depends on.

## Versioned, signed, distributable

Because a pack is just a manifest, it can travel. It's content-addressed by
checksum, so republishing the same version with different bytes is rejected —
versions are immutable. It can be **signed** with a publisher key; on install the
memory recomputes the checksum and verifies the signature against the tenant's
trust store, fail-closed. And it can live in a **global registry** — publish a
version, discover it, install the latest non-yanked or pin an exact one. It's
the npm-for-ontology pattern, with the supply-chain hygiene that implies.

Out of the box there's a six-pack industry library — real estate, fintech,
medical, legal, insurance, HR — as a starting point you can install, fork, or
ignore.

## Upgrades that don't orphan history

Ontologies drift. A pack gets a new predicate, retires an old one, tightens a PII
class. The upgrade path applies the **diff**: changed definitions are re-applied,
dropped predicates are deprecated (not deleted — their facts survive), new ones
are seeded. Uninstalling is the same discipline: predicates leave the active
vocabulary, the recorded facts stay put. You can evolve what your agent
understands without losing what it already knows.

## The shape of the idea

Keep the core small and generic. Push the domain into versioned, signed,
installable modules that namespace cleanly and never orphan a fact. Your agent
learns to speak medicine, or law, or real estate — and you never fork a line of
the memory to do it.
