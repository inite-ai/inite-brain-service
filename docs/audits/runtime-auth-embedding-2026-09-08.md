# Аудит сессий БД, прогрева эмбеддингов и готовности сервиса — 2026-09-08

Проверена `main` на `0cd331c`, включая исправления [#502](https://github.com/inite-ai/inite-brain-service/pull/502) и [#503](https://github.com/inite-ai/inite-brain-service/pull/503). Исправления по результатам этого аудита находятся в ветке `codex/runtime-auth-embedding-audit`. Это аудит кода и локальные проверки с SurrealDB 3.2.4 / драйвером 2.0.8; состояние данных и версия запущенного стороннего инстанса не проверялись.

## Фидбек обоснован

**Авторизация.** Ручной `signin()` переключает драйвер в режим, где он не переиспользует authentication provider из `connect()`. При стандартном часовом JWT драйвер начинает обработку истечения примерно за минуту до конца срока; без возможности обновить авторизацию он вызывает `invalidate()`. Поэтому «ровно через час» — приближение: важен срок JWT и таймер драйвера, а не uptime процесса. `version()` отвечает даже анонимному соединению и не доказывает работоспособность чтения.

На настоящей БД воспроизведены: успешный запрос, истечение короткого JWT, повторные `Anonymous access not allowed` при работающем `version()`. Исправление #502 переживает повторные истечения. Увеличение `DURATION FOR TOKEN` откладывает проблему, но не заменяет восстановление сессии. Возврат к root-пулу обходит симптом и расширяет полномочия соединений.

**Эмбеддинги.** BGE-M3 и OpenAI используют разные пространства: `bge-m3:Xenova/bge-m3:1024:l2` и `openai:text-embedding-3-small:1536:l2`. Сравнивать их нельзя. Даже одинаковая длина не сделала бы разные модели совместимыми. Колонка `option<array<float>>` допускает обе длины; неправильная строка может сломать весь cosine-запрос и построение HNSW. #503 блокирует несовместимые новые записи, фиксирует размерность DDL по основной модели и делает готовность зависимой от её прогрева.

Обвинять только библиотеку некорректно: поведение драйвера объясняет механизм, но приложение отвечает за выбранный контракт авторизации, допустимость fallback и проверку готовности. Конфигурация из штатного compose — часть поставки продукта.

## Что ещё нужно довести

**P1 — проверить и восстановить существующий корпус.** Защита новых записей не исправляет ранее записанные 1536-мерные векторы в BGE-корпусе. [`VECTOR_COLUMNS`](../../src/ai/embedder/embedding-space.ts) перечисляет 13 векторных колонок. `allTables=true` пока не покрывает `derived_representation.embedding`, `semantic_belief.embedding`, `lens_suppression.centroid`. Обычный reindex без этого параметра обрабатывает только факты. HTTP-задание `/v1/admin/maintenance/reindex` также пока не принимает `allTables`. Называть такой прогон полным восстановлением нельзя.

Для каждого tenant нужен read-only инвентарь: количество строк по длине вектора, отсутствующему/неожиданному `embeddingSpaceId`, отдельно для каждой из 13 колонок. Проверка только длины не обнаруживает смешение моделей одинаковой размерности. Затем — резервная копия, dry run, переиндексация поддержанных таблиц основной прогретой моделью, отдельное восстановление производных представлений/убеждений и переобучение centroid-модели, повторная проверка инвариантов и HNSW. Не удалять факты ради удаления плохого индекса. Конкретное наличие порчи на инстансе из фидбека пока не установлено.

**P1 — замкнуть readiness на эксплуатацию.** Docker healthcheck использует `/health`, маршруты backend в Traefik не включают `/ready`, периодическая readiness-проверка балансировщика здесь не настроена. Исправленный workflow обнаружит неготовый rollout, но сам по себе не выведет сломавшийся через час контейнер из маршрутизации и не откатит релиз. Нужна внутренняя readiness-проверка балансировщика и отдельный мониторинг реального read-запроса. При насыщении пула `pingScoped()` намеренно предполагает готовность; это не проверка всех соединений и не замена canary. Liveness, readiness и перезапуск процесса должны оставаться разными механизмами.

**P1 — завершить миграцию пространств до обещаний zero downtime.** [`EmbeddingSpaceService`](../../src/ai/embedder/embedding-space.service.ts) прямо сообщает, что подключение shadow dual-write ко всем записям и active-space фильтра ко всем поисковым веткам ещё не завершено. Переключить `EMBEDDER_PROVIDER` и сразу считать старый корпус совместимым нельзя. Обратное переключение на OpenAI тоже требует согласования с данными. До завершения этого механизма безопаснее отдельное окно миграции с проверенным восстановлением.

**P2 — закрыть обход общей защиты векторов.** [`LensAdminController`](../../src/synthesize/lens-admin.controller.ts) проверяет конечность чисел centroid, но не размерность или модель. [`fitAndPersist`](../../src/synthesize/lens-suppression.service.ts) записывает внешний массив напрямую. Сейчас он может иметь неправильную длину или происходить из другой модели. Нужен обязательный `embeddingSpaceId` и проверка пространства на входе, а не только `number[]`.

**P2 — показывать неполный reindex как неполный.** 503 больше не проглатывается, но другие ошибки tenant/batch по-прежнему могут логироваться и пропускаться. Результату нужны `failedTenants`, `failedBatches`, явный статус partial и повторяемые курсоры. `factsUpdated=0` не должен сам по себе означать успешное восстановление.

**P2 — не переоценивать scoped-пул и статические тесты.** `brain_caller` — namespace EDITOR, системный пользователь. Комментарии [`SurrealService`](../../src/db/surreal.service.ts) прямо указывают: table/field PERMISSIONS для него не создают заявленную PII/ABAC-границу; фактическое фильтрование выполняется приложением. Отдельно: тест `embedding-space-truth` классифицирует колонки и убирает расходящиеся константы размерности. Он не делает запись неправильного массива в БД невозможной и не доказывает защищённость всех будущих writers.

## Проверки, предотвращающие повторение

1. В обязательном CI держать реальные короткие JWT: два истечения подряд, живой токен после ручной invalidation, закрытие/восстановление обеих scoped-сессий, запрет ROOT-метаданных после восстановления. Не подменять время процесса для проверки таймеров живого драйвера.
2. Для каждого обновления SurrealDB/драйвера прогонять этот контракт; дополнительно проверять отзыв/ротацию credentials и разрыв сети. Приложение должно либо восстановиться, либо дать наблюдаемую ошибку без повышения полномочий.
3. Для эмбеддингов тестировать прогрев, постоянный отказ и восстановление primary: отказ до обращения к несовместимому fallback, отсутствие неправильных durable-векторов, отсутствие ложного успеха reindex. Для новых провайдеров проверять не только длину, но и модель/нормализацию.
4. В nightly/staging добавить длительный canary за реальной границей JWT, запускающий caller-facing чтение и запись. Короткий интеграционный тест проверяет механизм быстро; настоящий часовой прогон в рамках этого аудита не выполнялся.
5. При добавлении новой векторной колонки требовать указать writer, способ проверки пространства и процедуру backfill/repair. Классификация без восстановления недостаточна.

## Локальная валидация

Исходная проверка #502: 5 тестов на настоящей БД прошли. Новые проверки до патча воспроизвели потерю авторизации при свежем JWT, четыре проблемы DB/readiness и проглатывание 503 reindex. Полный unit-прогон с coverage: 396 suites / 4844 tests прошли. После последующих точечных правок отдельно перепроверены изменённые ветки. Интеграционный прогон: 4 suites / 20 tests на настоящем SurrealDB прошли, включая смешение размерностей и поломку cosine/HNSW. Typecheck, lint и build прошли; конкретный итог проверок указан в PR. Реальная загрузка ONNX и внешний production rollout этим аудитом не выполнялись; guard прогрева проверяется управляемыми провайдерами.
